# The verify gate judges standard reports under trust rules; it does not trust them

The verify gate measured everything itself and only understood `node:test` output, so every new stack would need its own hand-written measurer. We adopt a **report contract**: each stack's own mature tools run the tests and write standard reports, and the gate reads them and decides. Test results come as **JUnit XML** (this ADR, ticket #57); coverage as **lcov** and mutation as the **mutation-testing-elements JSON schema** follow under the same rules (#58, #59). An **adapter** setting in `verify.config.json` chooses how a project is measured; `node` (the default) keeps the built-in `node:test` measuring unchanged.

The gate stays the judge, not the report. The trust rules:

1. **A non-zero exit fails**, whatever the report says.
2. **The gate owns the report location.** A fresh directory outside the project is created after the run starts, for every run (main run, each replicate, holdout, journeys), and deleted after reading. The gate builds the reporter flags itself and appends them to the command; a project's config never chooses the path. Where a tool has no flag for the path (Playwright), the gate sets the variable it reads (`PLAYWRIGHT_JUNIT_OUTPUT_FILE`) only in that one child process (spike amendment 2 on #55).
3. **Only a report written during the run counts.** A missing file, a file modified before the fresh report directory was created (both times read from the same filesystem, so no rounding), or a file that does not parse fails the step, and the message names the flags the gate appended.
4. **Two witnesses must agree.** The JUnit totals (tests, failures, skipped) must equal the runner's own stdout summary, or the gate fails showing both and trusts neither.
5. **Holdout stays hidden.** For the hidden holdout only counts are printed; any trust failure becomes one fixed message, and the JUnit reader's errors carry a character offset at most, never text from the report.
6. **A weaker gate is an owner decision, never a silent pass.** While an adapter cannot run a check (for `junit`: test quality; coverage for a runner without lcov, #58; mutation without `mutation.command`, #59), the gate fails unless `verify.config.json` holds `weakerGate: {missing, decision}` whose `missing` equals exactly the checks not run and whose `decision` points at the owner's record. An accepted weaker gate still prints the checks it does not run on every run. The pipeline checks the record itself in #62.

Skipped and todo tests fail as before, journey ids are matched against passing JUnit test names, and failing tests are printed as `not ok N - <name>` lines in the existing "Failing tests" block, so the no-progress breaker and failure clustering read them unchanged.

## Considered Options

- **Keep writing a measurer per language**: full control, but every stack is a rewrite of coverage, mutation and output parsing, and the result is weaker than the tools each ecosystem already trusts. Rejected.
- **Trust the project's reports as written**: simplest, but a stale, hand-written or redirected report would pass a broken build. Rejected; the trust rules above exist for this.
- **Parse each runner's console output only**: no files to manage, but console formats change between versions and carry no per-test status we can rely on. Used only as the second witness.
- **An XML library**: the harness stays dependency-free, so `lib/reports/junit.js` is a small reader for the subset runners write and refuses anything else.

## Consequences

- Adding a stack means an adapter (flags in, report out, summary line), not a rewrite; a stand-in runner written in shell proves the gate is not tied to JavaScript.
- A check the `junit` adapter cannot run (test quality always; coverage for a runner without lcov; mutation without `mutation.command`) prints as "not available"; it passes only with a matching `weakerGate` owner decision, and lists them as not checked on every run.
- Coverage from lcov (#58) follows the same rules: the gate appends the coverage flags, the lcov lives in the run's report directory and must be fresh and parsable, and the set of source files comes from `srcDirs`, so a file missing from the report fails by name. The record must fit the file (no line past its end; no empty record for a non-blank file), and coverage ignore comments in measured files fail, since `coverage.exclude` (printed as a weakening) is the only visible way to leave code out. lcov has no second witness, so a forged report that fits the source is not caught by the gate alone. A runner that writes lcov (`vitest`) therefore drops `coverage` from its `weakerGate.missing`.
- Mutation from the mutation-testing-elements report (#59) follows the same rules where `mutation.command` is set: Stryker has no flag for the report path, so the gate writes its own Stryker config file into the run's report directory and passes it as the positional argument with `--testRunner --mutate --reporters json --checkers --tempDirName` (spike amendment 1 on #55); the project's Stryker config is not read and `--incremental` is never passed. `--mutate` is a sample seeded from the source, every sampled file must appear in the report, and the report's own `config` must show the gate's sample and no incremental run. Score = (Killed + Timeout) / (Killed + Timeout + Survived + NoCoverage); CompileError and RuntimeError are counted apart; `Ignored` mutants fail unless the owner lists them in `mutation.ignored`, which is printed as a weakening with `mutation.exclude`; exceeding `mutation.budgetMs` fails. Mutation then counts as checked and leaves `weakerGate.missing`; without `mutation.command` it stays "not available".
- `standin-pytest` is a test-only runner shape for the shell stand-in; offering Python as a stack needs its own spec.
- Hard to reverse: once products are built against the contract, changing report formats or loosening a trust rule changes every product's gate. Tightening stays cheap.
- Remaining risk: test code runs with the same rights as the tool, so it could write a consistent fake report and a matching summary. The gate-owned path outside the project and the protected config make that deliberate cheating rather than an accident; an independent review is still the backstop.
