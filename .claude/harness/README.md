# Harness: unattended build loop

A small, dependency-free guardrail layer for running agents to completion without a human in the loop.
The agent decides *how*; the harness decides *when it is done* and *what it may never do*.

| Piece | File | What it enforces |
|---|---|---|

| Circuit breaker | `lib/stop-loop.js` | Halts when the same failure (numbers stripped) repeats `--stall` times. |
| Time budget | `lib/stop-loop.js` | `--max-minutes N` halts (`halted-time`) once the run is older than N minutes, checked on each failing Stop attempt. |

## Learning loop (record, score, propose, measure)
```bash
node .claude/harness/bin/report.js            # what keeps going wrong
/harness-improve                              # read-only agent proposes one fix, you review and merge
node .claude/harness/bin/report.js --mark "merged port-discovery skill"   # later reports show before/after
```
Traces live in `.harness/` (gitignored, local to the machine). In an ephemeral cloud container they vanish with it:
copy `.harness/traces/` somewhere durable (artifact store, bucket) before the container is reclaimed, or run the report in the same session.
The scorers are deterministic and cheap. Subjective rubrics (verbosity, redundant tests) need an LLM judge reading the same traces; not built yet.
The improver is untrusted-input aware: traces are data, and it may not propose widening permissions or touching hooks, deny rules, harness code or CI.

## Use
```bash
node .claude/harness/bin/harness.js init --verify "npm test" --task-file spec.md --protect acceptance/ --max 15
# ... agent works; Stop hook loops it until green or halted ...
node .claude/harness/bin/harness.js status
node .claude/harness/bin/harness.js off      # human escape hatch
node .claude/harness/bin/harness.js restore  # after a crash: put the last checkpoint's files back (fetches from origin if needed)
```
Or `/harness-build <spec> --verify "<cmd>"`. Start Claude with `--permission-mode auto` (or `acceptEdits` + the allow list
in `.claude/settings.json`), never `--dangerously-skip-permissions`.

## Strong verify (`bin/verify.js`)
`--verify "node .claude/harness/bin/verify.js"` with a `verify.config.json` (see [`fixtures/todo-api/`](fixtures/todo-api/) for JavaScript, [`fixtures/slug-ts/`](fixtures/slug-ts/) for TypeScript). Seven checks, in order:
1. **Tests**: exit 0, none skipped or todo, at least `minTests` ran. Then **replicates** (`replicates`, default 2): the same command runs again and must give the same pass/fail counts, otherwise the gate is noise and is rejected as flaky. `--fast` skips the extra runs.
2. **Type check** (optional, TypeScript: `"typecheck": {"command": "npx tsc --noEmit", "timeoutMs": 120000}`): runs after the tests and fails the gate with the tail of the compiler output. Node strips types without checking them, so without this a type error never fails anything. Off when the key is absent. `--fast` still runs it: it is cheap and it is exactly the feedback the agent needs while iterating. The harness never installs or bundles `tsc`; the command is yours.
3. **Source coverage**: line coverage of `srcDirs` only, from raw V8 coverage across *all* processes (so a server spawned by an acceptance test counts). Total and per-file floors. For `.ts` files, lines that hold only types (`interface`, `type`, `import type`) are not counted as executable.
4. **Test quality**: each test file in `testQuality.dirs` must reference `src/`, contain at least N real assertions, and no tautologies (`assert.ok(true)`) or skips. This is what rejects a placeholder `smoke.test.js`. Type arguments and casts (`assert.deepEqual<T>(...)`, `assert.ok(true as boolean)`) are understood.
5. **Holdout** (optional, `"holdout": {"command": "node --test \"/abs/holdout/*.test.js\"", "minTests": 1}`): hidden acceptance tests run only here, only after checks 1-4 pass. The agent is told just `holdout: K of N hidden acceptance test(s) fail`: no names, paths or expected values. An empty or deleted holdout fails. `--fast` skips it.
6. **User journeys** (optional, `"journeys": {"command": "node --test \"journeys/*.test.js\"", "uxFile": "docs/ux.md", "minTests": 1}`): browser tests of the product as a person uses it, run after checks 1-5 pass. They must pass with none skipped, and when `uxFile` is set every journey or UI-check id in it (`J1`, `UC3`) needs a passing test whose name contains that id. Failures are shown in full. Start from `templates/journeys.test.js` (Playwright under `node:test`). The harness does not install a browser, and it cannot tell a real walkthrough from a test that only carries the right name, so an independent QA pass is still worth having. Journey runs do not count toward source coverage. `--fast` skips it.
7. **Mutation spot-check**: flips one operator (`===`/`!==`, `&&`/`||`, `>=`/`>`, `true`/`false`) in a copy of `src/` for a seeded sample of mutants; the suite must fail on at least `minKillRate` of them. Survivors are printed as `file:line op -> op`, which is concrete feedback for the agent. A mutant that hangs the suite counts as killed; the timeout is 3x the healthy run time (floor 10 s).

`--fast` skips replicates, holdout, journeys and mutation for quick iteration (the type check still runs); the full run is the definition of done. Protect `verify.config.json` and `acceptance/` with `--protect`; the script itself is already read-only under `.claude/`.

### TypeScript
Supported: projects that run tests with Node's built-in runner and native type stripping, e.g. `"testCommand": "node --test \"tests/*.test.ts\""` (Node 22.18+ or 23.6+; earlier 22.x/23.x need `--experimental-strip-types`, put it in your own `testCommand`). Files ending `.ts`, `.mts` and `.cts` count as source and test files (`*.test.ts`, `*.spec.ts`); `.d.ts` files never count as source. Use erasable syntax only (no `enum`, `namespace` or parameter properties); import siblings with the `.ts` extension.
- **Mutants only land in runtime code.** For a TypeScript file the gate asks `node:module`'s `stripTypeScriptTypes` for the type-erased text (types are overwritten with spaces, so offsets and line numbers equal the original), and only looks for operators in what survives. A `true` in `strict: true`, the `>=` in `Array<T>= []`, `false` in `T extends true ? false : never`, or anything in an `interface` or `type` is never a mutation site, so no mutant is falsely "killed" by a syntax error or falsely "survives" because stripping erased it. Every mutant must also still parse after stripping, or it is dropped (the plain-JS filter cannot do this for ES modules). A source file that cannot be stripped fails the mutation step by name instead of being skipped. This needs `module.stripTypeScriptTypes` (Node 22.13+/23.2+); the experimental-warning it prints is silenced.
- **Coverage offsets** from V8 already refer to the original text for stripped files, so uncovered lines are the line numbers in your `.ts` file.
- `.tsx` and `.jsx` are **not** supported on this path: Node's type stripping does not handle JSX, so such files are ignored as source (they are not measured or mutated). They count as source and test files only with `"adapter": "junit"` and a runner that compiles JSX (`vitest`), or with `"adapter": "vitest-stryker"`; see the report contract below.
- Not supported on this path: Vitest and Jest (the gate parses `node:test` output; use the `vitest-stryker` adapter below for Vitest), `--experimental-transform-types` (it changes offsets, so mutation fails closed on such files).

Requirements and limits: Node/`node:test` projects (JavaScript, or TypeScript as above); the mutation run copies `srcDirs`, the test dirs and `mutation.copy` to a temp dir (add `tsconfig.json` there if your test command reads it), first proves that copy passes its own tests, and never touches your real files; a child process that is killed by a signal writes no coverage, so servers must handle `SIGTERM` and exit 0 (the gate says so when a file shows 0%); the mutation operator set is small and equivalent mutants make 100% unrealistic, hence a 60% default floor; the sample changes with the source (seeded from it) so the agent cannot memorise it. Not covered: logic placed outside `srcDirs`, non-`node:test` runners, JSX, and deleting a source file (set `coverage.minSourceFiles`; the git-tracked list is not consulted).

### Report contract (`"adapter": "junit"`, ADR-0003)
With `"adapter": "junit"` the gate judges test results from a **JUnit XML** report written by the project's own runner, so the runner need not be JavaScript. Without `adapter` (or with `"node"`) nothing changes.
```json
{ "adapter": "junit", "runner": "vitest", "testCommand": "npx vitest run",
  "holdout": { "command": "npx vitest run --root /abs/holdout" },
  "journeys": { "command": "npx playwright test", "runner": "playwright", "uxFile": "docs/ux.md" },
  "weakerGate": { "missing": ["test-quality", "mutation"], "decision": "decisions.md: weaker gate for slug-react, 2026-11-24" } }
```
`runner` (`vitest` or `playwright`; `holdout.runner` and `journeys.runner` default to it) says which flags the gate appends to the command and which stdout summary it reads: Vitest `--reporter=default --reporter=junit --outputFile.junit=<file>`, Playwright `--reporter=junit,line --output=<dir>` with the report path in `PLAYWRIGHT_JUNIT_OUTPUT_FILE`, set only for that child process. `standin-pytest` (pytest's `--junitxml=<file>` and `=== N passed in Xs ===` line) exists **only for the harness's own tests**: it is the shape of the shell stand-in runner, not a supported stack (Python is outside #55). The flags go at the end of the command, so the command must end with the runner itself (`npm test -- ` style wrappers need the `--`).
- **Trust rules.** A non-zero exit fails whatever the report says. Every run (the main run, each replicate, the holdout, the journeys) gets a fresh report directory outside the project (symlinks resolved), created after the run starts and deleted after reading; the gate refuses to start if the temp directory is inside the project. A missing report (the message names the flags), one modified before the report directory was created (both times from the same filesystem, so no rounding), a malformed one, or one whose totals (tests, failures, skipped) differ from the runner's own summary line fails the step, showing both sets of numbers.
- **Same checks as the node path.** Skipped and todo tests fail, `minTests` and replicates apply, and journey ids in `uxFile` must each have a passing JUnit test whose name contains them. Failing tests are printed as `not ok N - <name>` lines with an `error:` line in the "Failing tests" block, so the no-progress breaker and failure clustering work unchanged.
- **Holdout stays hidden.** Only counts are printed. A holdout report that cannot be trusted (missing, old, malformed, totals disagree) gives one fixed message, `holdout: the JUnit report could not be trusted (parse or totals problem); details hidden`, and the JUnit reader's own errors carry a character offset at most, never report text.
- **Coverage from lcov (#58).** For a runner that can write lcov (`vitest`), the main test run also gets `--coverage.enabled --coverage.reporter=lcovonly --coverage.reportsDirectory=<dir> --coverage.include=<srcDir>/** --coverage.reportOnFailure` (one `include` per `srcDir`, so untested files appear at 0%, and a failing run still writes lcov), into the same gate-owned directory under the same trust rules: a missing, older-than-the-run or malformed lcov fails the coverage step. `lib/reports/lcov.js` reads `SF:`/`DA:`/`LF:`/`LH:` (other `KEY:value` records are skipped), checks that `LF`/`LH` agree with the `DA:` lines, and refuses anything else with a line number. `SF:` paths may be relative to the project root or absolute (the project's real path also counts), with `\` separators; on Windows and macOS letter case is ignored (only when exactly one source file fits), on Linux it must match exactly. Duplicate records for one file merge by the highest hit count per line. **The file set comes from `srcDirs`, never from the report:** a source file with no record fails, naming the file. `minLines`, `minFileLines` and `minSourceFiles` apply as on the node path, with uncovered line ranges printed, and a test file inside `srcDirs` fails. The record must also fit the file: a `DA:` line past the file's last line fails, and a record with no executable line fails unless the file is blank once comments and whitespace are removed (a type-only file therefore fails; put it in `coverage.exclude`).
- **Coverage ignore hints fail.** `v8 ignore`, `c8 ignore`, `istanbul ignore` and `node:coverage ignore` comments (any form, any letter case) make lines vanish from lcov, so on the lcov path every source file is scanned and each hint fails, naming file and line. A file in `coverage.exclude` is not scanned: excluding it is the visible way to leave code unmeasured. The node path does not scan (its pass/fail is unchanged). `.tsx`/`.jsx` count as source and test files only for a runner that declares JSX (`vitest`); the node path and other runners keep their patterns. Replicates, holdout and journeys are not measured.
- **`coverage.exclude` is a weakening.** On every adapter the excluded paths are printed in the coverage step (`weakening: coverage.exclude leaves ... unmeasured`) and again at the end of the result (`weakened (verify.config.json): coverage.exclude ...`).
- **Weaker gate needs an owner decision.** Checks an adapter cannot run print `not available for the junit adapter`: test quality for every runner (the `vitest-stryker` preset runs it), mutation when no `mutation.command` is set (see below), and coverage for runners without lcov (`playwright` as the main runner, `standin-pytest`). While any check is not available, the gate **fails** unless `verify.config.json` has `"weakerGate": {"missing": [...], "decision": "..."}` whose `missing` equals exactly the checks not run (for `vitest`: `test-quality`, `mutation`, or just `test-quality` once `mutation.command` is set; listing a checked step there fails as "listed but checked"; an extra or a missing entry fails) and whose `decision` points at where the owner recorded it (a `decisions.md` line or an issue). Once accepted, every run still ends with `not checked (weaker gate, junit adapter): ... (owner decision: ...)`. The gate checks the list, not the record itself; in a whole-pipeline run the plan phase also needs `design.md`'s `## Stack` section to take `option: weaker gate` with a line `Weaker gate: <checks>` naming exactly the same checks (#62); `design.md` is hashed with the `spec-approved` approval, so the owner approves the weaker gate there (a `decisions.md` line alone does not count).
- **Known limit of the reader.** It reads the XML subset runners write (a `>` inside a quoted attribute is fine) and refuses everything else (unknown entities, unquoted attributes, DTD tricks it cannot follow): it fails safe rather than guessing.
- **Remaining risk.** Test code runs with the same rights as the runner, so it could write a consistent fake report *and* print a matching summary. The gate-owned path outside the project, the flags appended at run time and a protected `verify.config.json` make that deliberate cheating rather than an accident, which review and the hidden holdout are there to catch; the gate alone cannot rule it out. A report copied in with a fresh modification time is likewise caught only by the summary check. File times have the filesystem's granularity (the kernel's coarse clock, a few milliseconds), so a report written within that window before the run starts cannot be told apart from one written during it. For lcov there is no second witness: a consistent forged lcov is caught only where it does not fit the source (a missing file, a line past the end, no lines for a non-empty file), and the hint scan reads comments only, so other ways of hiding code from the coverage tool (project coverage config, which #60 protects) are not seen by it.

#### Mutation from Stryker's report (#59)
With `"adapter": "junit"` and a `mutation.command`, the mutation step is judged from Stryker's **mutation-testing-elements** JSON report instead of the built-in sampler; mutation then counts as checked, so `weakerGate.missing` must no longer list it (the exact-match rule still applies).
```json
"mutation": { "command": "npx stryker run", "testRunner": "vitest", "samples": 6, "minKillRate": 0.6, "budgetMs": 300000,
              "checkers": [], "ignored": [{ "file": "src/Slug.tsx", "line": 24, "mutator": "StringLiteral" }] }
```
- **The gate builds the run.** Stryker has no flag for the report path, so the gate writes its own config file (only `jsonReporter.fileName` and `incremental: false`) into a fresh directory outside the project and passes it as the positional argument, then `--testRunner <mutation.testRunner> --mutate <sample> --reporters json --checkers <mutation.checkers> --tempDirName <gate dir>`. The project's own `stryker.conf.*` is not read, Stryker's sandbox never lands in the project, and `--incremental` is never passed (`mutation.incremental` is refused). `mutation.command` must therefore end with `stryker run`. The TypeScript checker is off by default (`checkers: []`, +68% time in the spike); `tsc --noEmit` as `typecheck.command` is the type check.
- **Seeded sample.** `--mutate` lists up to `mutation.samples` source files from `srcDirs` (the same file set as coverage, so `.tsx`/`.jsx` count for `vitest`; files in `coverage.exclude` or `mutation.exclude` are left out), chosen with a seed taken from the source text as on the node path: the same source gives the same sample, a changed source gives another, so the agent cannot memorise it (as on the node path, any edit to the source, whitespace included, moves the sample; it cannot be chosen without knowing the seed function's output). On this path `mutation.samples` counts files, and the step says so. Every sampled file must appear in the report, and a file the gate did not ask for, a report whose `config.mutate` is not the sample, or one that says it ran incrementally is refused.
- **Score** = (Killed + Timeout) / (Killed + Timeout + Survived + NoCoverage) against `mutation.minKillRate`; a Timeout counts as killed, as on the node path. CompileError and RuntimeError are left out of the score and their counts printed. Each Survived and NoCoverage mutant is printed with file, line, mutator and replacement. A report with nothing scoreable fails.
- **Ignored mutants fail** (a `// Stryker disable` comment cannot hide weak tests) unless the owner lists them in `mutation.ignored` as `{file, line, mutator}`; accepted ones are printed as a **weakening** in the step. `mutation.exclude` and `mutation.ignored` are listed with `coverage.exclude` in the closing `weakened (verify.config.json): ...` line of every run.
- **No peeking at the active mutant.** Before Stryker runs, every source and test file under `srcDirs`, `testQuality.dirs` and `acceptance/` is scanned; a line mentioning `__stryker__` or `STRYKER_ACTIVE` (any case) fails the step, naming file and line, since tests that know which mutant runs could fail on purpose and make every mutant look killed. A hidden holdout outside the project is not scanned.
- **Budget.** `mutation.budgetMs` (default 300000) bounds the whole step; exceeding it fails with the time used. The per-mutant `mutation.timeoutMs`, `timeoutFactor` and `minTimeoutMs` keep their node-path meaning and are not passed to Stryker (its own per-mutant timeouts apply).
- **Trust rules** as for JUnit: a non-zero exit fails, and a missing, stale or malformed report fails, naming what the gate passes. Stryker prints no totals line worth a second witness, so the cross-checks are the report's own `config` and its file set.
- These keys apply only with `"adapter": "junit"`; the node adapter refuses them and keeps its built-in sampler. Tested with `test/fixtures/standin-stryker.js`, a stand-in for `stryker run` that takes the same config file and flags, and with the spike's real reports (54.5% without and 55.6% with the TypeScript checker).

#### The `vitest-stryker` adapter: React and TypeScript web apps (#60)
`"adapter": "vitest-stryker"` is a preset on the report contract for Vite + React + TypeScript projects: Vitest runs the tests (JUnit and lcov, as above), Stryker with its vitest runner runs mutation (as above), Playwright walks the journeys, and a type check is **required**. Test quality runs too (the JS checker, `.tsx` tests included), so the gate is **full**: nothing is "not available" and `weakerGate` is refused. The proven setup is `fixtures/slug-react/`.
```json
{ "adapter": "vitest-stryker", "minTests": 10, "srcDirs": ["src"],
  "coverage": { "minLines": 90, "minFileLines": 80 },
  "holdout": { "command": "npx vitest run --dir \"${HARNESS_HIDDEN_DIR:-hidden-tests}\"", "minTests": 3 },
  "journeys": { "command": "npx vite build && npx playwright test", "uxFile": "ux.md" },
  "mutation": { "samples": 6, "minKillRate": 0.8, "budgetMs": 240000 } }
```
- **What the preset fills in** (each can be overridden, except where noted): `runner: "vitest"` (fixed), `testCommand: "npx vitest run"`, `typecheck.command: "npx tsc --noEmit -p tsconfig.json"` (a command can replace it; `"typecheck": null` or `false`, and a command that does nothing (`true`, `:`, `exit 0`, empty), are refused, because Vitest and esbuild strip types without checking them), `mutation.command: "npx stryker run"`, `mutation.testRunner: "vitest"` (fixed), `mutation.checkers: []` (Stryker's TypeScript checker is off: +68% mutation time in the spike for 4 reclassified mutants; `["typescript"]` opts in), `holdout.runner: "vitest"` and `journeys.runner: "playwright"` (fixed). For any other combination use `"adapter": "junit"` with `runner`.
- **Test quality** is the node path's check on `testQuality.dirs`, reading `.test`/`.spec` files with `.ts`, `.tsx`, `.js`, `.jsx`: each must reference the source, hold `minAssertionsPerFile` assertions (`expect(...)` and `expect<T>(...)` count) and no tautology (`expect('a').toBe('a')`, `expect(true).toBeTruthy()`, `expect<number>(1).toBe(1)`) or skip. `testQuality.srcAliases` (e.g. `["@/"]`; each entry must end with `/`) counts an import through a path alias as a source reference.
- **Protected tool configs.** When `verify.config.json` names this adapter, `stryker.conf.*`, `stryker.config.*`, `vitest.config.*`, `vitest.workspace.*`, `vite.config.*`, `tsconfig*.json` and `playwright.config.*` are protected like `verify.config.json`: `harness.js init` adds them to the run's protected paths (the Write/Edit and Bash guards refuse them while the run is active), and `bin/check-protected.js` adds them when the **base** branch's `verify.config.json` names the adapter. They match by file name at any depth (`apps/web/vite.config.ts` too). A config file that a command in `verify.config.json` names with `--config`, `-c`, `--project`, `-p` (tsc) or `--config=`/`--project=` is protected as well (project-relative paths only). With `"adapter": "junit"` the same configs are looked up by what runs: `vitest.config.*`, `vitest.workspace.*` and `vite.config.*` for a `vitest` runner (main, holdout or journeys), `playwright.config.*` for `playwright`, `stryker.conf.*`/`stryker.config.*` with a `mutation.command`, `tsconfig*.json` with a `typecheck.command`. **Limits:** files a config loads are not found, because reading them would mean executing the config: Vitest `setupFiles` and `globalSetup`, and a tsconfig's `extends` target unless it is itself named `tsconfig*.json` (keep shared bases named so, e.g. `tsconfig.base.json`). Review catches edits to those. A whole-pipeline run (`--open-gate-files`) does not protect them, as it does not protect `verify.config.json`; `pipeline.js` freezes them by hash instead (below).
- **Setup in the project, not the harness.** Vitest, `@vitest/coverage-v8`, jsdom, Stryker (`@stryker-mutator/core` and `vitest-runner`), Playwright, React and TypeScript are the project's devDependencies, pinned exactly; the harness gains none. Pin `typescript` to `^6`: TypeScript 7 has no JavaScript API and breaks Stryker 10.1.1 even without the checker. Put tests in `tests/` (a test file under `srcDirs` fails), set `test.dir` and `test.include` in `vitest.config.*` so the main run does not pick up the holdout set, and make the entry file (`main.tsx`) testable or list it in `coverage.exclude` (printed as a weakening). The holdout command points Vitest's `--dir` at `${HARNESS_HIDDEN_DIR:-hidden-tests}`; a hidden set outside the project needs `server.fs.strict: false` in `vitest.config.*` and an import alias (`@/`) instead of relative imports. The journey serves the built app with a small server that exits 0 on `SIGTERM`; set `PLAYWRIGHT_CHROMIUM_EXECUTABLE` in `playwright.config.*` to use a browser that is already installed.
- **Run it** from the project: `CLAUDE_PROJECT_DIR=$PWD node .claude/harness/bin/verify.js` (for the fixture: `cd .claude/harness/fixtures/slug-react && npm ci && CLAUDE_PROJECT_DIR=$PWD node ../../bin/verify.js`, about 30 s here, 18 s of it Stryker). The fixture passes at a 100% kill rate (`minKillRate: 1`, 38 mutants), and each deliberate weakening fails for its own reason: a removed assertion (surviving mutants), an untested file (coverage), a `// Stryker disable` comment (Ignored mutant), an edited `vitest.config.ts` (protected file, in session and in CI) and a type error (type check). The harness's own tests use stand-ins (`test/vitest-stryker.test.js`) and never need the fixture's `node_modules`.

Neutrality is tested with `test/fixtures/standin-runner.sh`, a POSIX shell script that behaves like pytest, and with replays of the real Vitest and Playwright reports from the spike (`test/fixtures/reports/`, `docs/process/spike-gate-adapters.md`).


## Adapters
An adapter is how the gate measures one stack. It is chosen with `"adapter"` in `verify.config.json`; the gate stays the judge and the stack's own tools only write reports (ADR [0003](../../docs/adr/0003-report-contract.md)).

| Adapter | Commands | Reports read | Protected tool configs | Test quality | Proven by |
|---|---|---|---|---|---|
| `node` (default) | `testCommand` on `node:test`, optional `typecheck` | `node:test` output, raw V8 coverage, built-in mutation sampler | `verify.config.json` | yes | the harness suite |
| `junit` | `testCommand` with `runner` (`vitest`, `playwright`); optional `typecheck`, `holdout`, `journeys`, `mutation.command` | JUnit XML, lcov (`vitest`), Stryker JSON with `mutation.command` | by what runs (see above) | **no**: needs a `weakerGate` owner decision | report replays and stand-ins |
| `vitest-stryker` | preset: `npx vitest run`, `npx tsc --noEmit` (required), `npx stryker run`, Playwright journeys | JUnit XML, lcov, Stryker JSON | `vite`/`vitest`/`stryker`/`playwright` configs and `tsconfig*.json` | yes (`.tsx` included) | `fixtures/slug-react/`, CI job `gate-slug-react` |

**What an adapter provides.** (1) The commands it runs and the flags the gate appends to each, so reports land in a gate-owned directory outside the project. (2) The report formats it reads and the second witness for each (the runner's stdout totals for JUnit; the report's own `config` and file set for Stryker; none for lcov). (3) The tool config files that can change what is measured, which become protected while a run is active and in CI. (4) Whether the test-quality check can read its test files; where it cannot, the check is "not available" and the gate fails without a `weakerGate` owner decision.

**Trust rules** (ADR-0003): a non-zero exit fails; each run gets a fresh report directory outside the project, so only a report written during the run counts; a missing, stale or malformed report fails, naming the flags; report totals must match the runner's own summary; the holdout prints counts only; a check an adapter cannot run is a weaker gate the owner must accept, and it is printed on every run. **Remaining risks:** test code runs with the runner's rights, so it could forge a consistent report and summary (deliberate cheating that review and the hidden holdout are there to catch, not the gate); lcov has no second witness; files a tool config loads (`setupFiles`, a tsconfig `extends` target not named `tsconfig*.json`) are not protected; a whole-pipeline run (`--open-gate-files`) protects none of the configs.

**Adding an adapter.**
1. **Spike** the stack's real tools in a throwaway project: capture their reports into `test/fixtures/reports/`, measure the run, and write down every place a tool does not behave as the spec assumes (as in `docs/process/spike-gate-adapters.md`).
2. **Reuse the readers.** If the tools write JUnit XML, lcov or mutation-testing-elements JSON, use `lib/reports/` as is and add only the flags and the summary line; a new format needs its own reader with the same refuse-what-you-do-not-understand rule. Test with stand-ins and the captured reports, never with the stack installed in the harness.
3. **Fixture.** A small real project under `fixtures/<name>/` with exact pins and a lockfile that passes the full gate, and fails for its own reason under each deliberate weakening (a removed assertion, an untested file, an ignore comment, an edited config, a type error).
4. **CI job.** A job in `.github/workflows/ci.yml` that runs `npm ci` (or the stack's equivalent) with a cache keyed on the fixture's lockfile, installs what the journey needs, and runs the real gate in the fixture; add its name to `ci/ruleset.json` (applying the ruleset is the owner's step, `ci/protect.sh --apply`). `gate-slug-react` is the example.
5. **Catalogue entry** (#62): list the adapter, its versions and limits in the stack catalogue so kickoff can offer it.

## Whole-pipeline gate (`bin/pipeline.js`)
```bash
node .claude/harness/bin/harness.js init --verify 'node .claude/harness/bin/pipeline.js check --product app --docs docs/app' \
  --task "one-line idea" --open-gate-files --no-commit-gate --max 40 --stall 4
```
Run it in the product's own repository, not in `claude-setup`: a new product lives in its own repository or a path the owner gives. Set that repository up first (`repo-setup`, or `node .claude/harness/bin/setup-repo.js <product-repo>` from a clone of `claude-setup`; it installs the harness, enables the plugins, creates the labels and the repository docs, and prints one checklist; `init` refuses a `pipeline.js check` run, exit 2 with nothing written, while a checklist row is open, and `--labels-json <file>` gives it a saved copy of the labels where `gh` cannot reach GitHub), open the session in that repository, then run the `init` above with `--product` and `--docs` pointing inside it (`orch-product-team` uses `--product <product-repo> --docs <product-repo>/docs/product/<slug>`). The first `pipeline.js check` reports `discover` as the next phase.

The Stop hook only holds an agent while verify fails, so with `verify.js` as the command the agent is held during the build and free to end the turn (usually to ask a question) in every other phase. `pipeline.js check` is a verify command for the whole of `orch-product-team`: it checks the phases and the owner gates in order (brief, UX, look and key screens, gate `design-approved`, design, spec, gate `spec-approved`, plan, build, review, QA, release, gate `accepted`, retro; a product whose kickoff choice is no designed screens, and a run already past UX when its harness gained the design gate, has no look phase and no `design-approved`, and its spec phase records the look), stops at the first incomplete one and prints what is missing last, so that is what the Stop hook feeds back. The build phase runs the product's own `verify.js`; later phases are only looked at once it is green, and it is re-run on every check.

**Owner gates (`waiting`).** Phase 4a records the spec issue as a line `Spec issue: #N` in `decisions.md` (an issue in the product's own repository); the task list in the plan phase must be generated from that same issue. At each gate `pipeline.js` reads the issue's labels live (`gh api repos/{owner}/{repo}/issues/N`, run from the product directory). While the label is missing, or GitHub cannot be reached, the check exits 3 and its last line is `waiting for owner: spec issue #N needs label <gate>`. The Stop hook accepts that only from a verify command that runs `pipeline.js`: it holds the agent once so it can tell the owner, then lets the turn end, keeps the run active and charges no iteration. When the label is there, the next check moves on by itself. A read error other than "unreachable" (a wrong issue number, no access) blocks like any incomplete phase. `--issue-json <file>` gives a saved copy of the spec issue (from the GitHub MCP `issue_read` tool) for sessions where `gh` cannot reach GitHub; it is ignored while `gh` can. Each turn the hook lets end this way is traced as a `gate-wait`, and `agents-kpi.js` counts the next human prompt as a gate response (`human.gateResponses`), not an intervention. Once `spec-approved` passes, the spec issue number is pinned in `.harness/pipeline/`, and a different `Spec issue:` line fails the check. A pull request is never accepted as the spec issue. The Bash guard (`lib/guards.js`) refuses `gh` commands that add or remove `design-approved`, `spec-approved` or `accepted`. Limits: the labels are read with the session's own GitHub access, so GitHub cannot tell who added one; the guard does not cover the GitHub MCP tools or raw HTTP calls, and a saved copy given with `--issue-json` is written by the session (it is used only while `gh` cannot reach GitHub, and the report warns when it is). The first spec issue named is trusted, so in a repository with earlier labelled issues the owner checks the number in the waiting message. Every human prompt after a wait counts as a gate response, even one that changes scope.

**Design gate (`design-approved`, #149, ADR-0005).** In a new first run the `look` phase comes after UX: `decisions.md` needs `Spec issue: #N` (the spec issue is opened here, since the gate's label goes on it) and `Look:` lines, and `design-approved-page.md` (from `templates/design-approved-page.md`) needs its four sections filled with no code, at least one rendered link under "Look variations" and under "Key screens", and every local link pointing at an existing file in `screens/` beside the page. The gate then waits for `design-approved` on the spec issue like the other gates, with verdicts, redirects (impression there goes back to `look`; approach, correctness and craft are judged at later gates and are not read), the 3-round limit, and an approval tied to the page and `screens/`. Once it is passed, the `spec-approved` page's Screens section must link `design-approved-page.md` instead of asking about the look again. Whether the run has the gate is decided once, at its first check, and kept as `designGate` in `.harness/pipeline/<slug>.gates.json`: it is left out when the kickoff file (`<docs>/kickoff.json`) says `"design": "none"`, or when the run is already past UX (system design written, an approval given or the spec issue pinned), so an existing run is never sent backwards and keeps its approvals. The report then says `design gate: not in this run - <why>`, and a later kickoff edit only warns. Change runs do not have the gate yet (#152).

The plan phase writes the spec and tests inside the run, so start with `--open-gate-files` (the default write-protection of `spec.md`, `acceptance/` and `verify.config.json` is off). Instead, when the plan phase first completes, `pipeline.js` records hashes of `spec.md`, `verify.config.json`, `acceptance/`, `holdout/`, `ux.md` and the tool configs of the adapter that `verify.config.json` names (the protected list above, from `lib/protected.js`, in dot folders too; a config named in a command is hashed at its exact path, even under `node_modules`; none by name for `node`) in `.harness/pipeline/`. These configs count as plan output, so a correctness or craft redirect does not free them. Any later change, addition or deletion fails the check until `decisions.md` has an `AMEND: <path> - reason` line (one line per change). This is tamper detection with an audit trail, not prevention: it lets a test author correct a wrong test without a human, and it means the holdout is not hidden from the agent in this mode. `--no-commit-gate` is needed because the commit gate would refuse every commit until the last phase.

**Stack from the adapter catalogue (#62).** `adapters/catalogue.json` lists each adapter's stacks, product kinds, checks, missing checks, fixture and status (`proven`: fixture green in CI and a product built; `experimental`: fixture green only; `planned`: no adapter yet). `orch-product-team` reads it when proposing a stack; no always-loaded rule refers to it. The design phase is incomplete until `design.md` has a `## Stack` section with `Adapter: <id> (<status>)` (an adapter from the catalogue, its status exactly as listed, not `planned`) or `Unsupported: <stack>; option: supported alternative|weaker gate|adapter first` (the first two with the `Adapter:` line of the adapter that runs). The spec-approved page shows it as a `### Stack` part of "The real choices", with an adapter status. With `option: weaker gate` the section also needs `Weaker gate: <checks>`. The page part must also name an alternative, and all three options when the stack is unsupported. The plan phase needs that adapter in `verify.config.json` (a config without `adapter` counts as `node`), and stays incomplete for `adapter first`. **Breaking for runs in progress:** a run whose `design.md` has no `## Stack` section is sent back to the design phase on its next check. `test/catalogue.test.js` checks that every `proven` or `experimental` entry's fixture exists.

**Change runs (`--change <N>`, #89).** For a product whose first run is accepted, `pipeline.js check --product <dir> --docs <dir> --change <N>` walks one change request on its own spec issue #N: `spec` (the issue is readable; #91 adds a one-page change spec check), gate `spec-approved` on #N, `plan` (the product's gate files still in place, and `<docs>/changes/<N>/TASKS.md` generated from #N), `build` (the product gate), `review` and `qa` (`reviews.md` and `qa.md` in `<docs>/changes/<N>/`), `release` (README run steps, and the product `CHANGELOG.md` names `#N`), gate `accepted` on #N. Waiting, exit 3 and the waiting line, layer verdicts, redirects (problem, impression and approach go back to the change's `spec`, correctness and craft to `build`), the 3-round limit and approvals tied to file hashes (`spec-approved`: the files in `<docs>/changes/<N>/` other than its logs; `accepted`: the product) work as in a first run. The product's frozen files are compared with its last owner-accepted state, not with what is on disk at the change's first check: the frozen hashes recorded when the latest change passed `accepted` (`.harness/pipeline/<slug>.accepted.json`, written only then), or else the first run's freeze. So an edit made before the first check needs an `AMEND:` line too, an accepted change's amended files are not explained again by the next change, and an unaccepted change's edits never become a baseline. The change's `AMEND:` lines are read from `<docs>/changes/<N>/decisions.md` only. Its state is `.harness/pipeline/<slug>.change-<N>.*`; the first run's state and records are only read. On the first successful read of issue #N, a change run refuses to start (exit 2) if the issue already carries `accepted` or is closed (a wrong number, or a fresh clone without `.harness/`); `spec-approved` alone is allowed, as the owner may approve the change spec before the run starts. Nothing is recorded while GitHub cannot be reached. Once the change has passed `accepted`, any difference in the files the owner judged (both gates' approved files and the product's frozen files) is refused as new work (exit 2, "open a new issue"), with or without an `AMEND:` line; undoing it lets the re-check pass again. Any other cause on a re-check (GitHub unreachable, a drifted task list) is reported as in any run. The number is a flag rather than a `Change:` line in `decisions.md` so that it is fixed in the verify command for the whole harness run and the first run's `decisions.md` stays untouched. It refuses to start (exit 2) unless the first run's `accepted` approval or an accepted change is on record, and when `<N>` is the first run's spec issue. Limits: the start check reads the records and does not re-hash the product, since the change itself changes it; a first-run check after an accepted change reports the change's edits as voiding the first run's `accepted` (later changes still start, from the accepted baseline).

Limits: the document checks are structural (the file exists, is not a stub, has the required section or line), so they prove a phase was done, not that it was done well; `reviews.md` reports its own open-finding counts; every stop attempt after the plan phase costs a full product gate run.

## Holdout set (`--hide`)
```bash
node .claude/harness/bin/harness.js init --verify "node .claude/harness/bin/verify.js" --hide /abs/path/holdout --protect acceptance/
```
The human writes extra acceptance tests from the spec and keeps them **outside the project tree** (recommended). `--hide` makes the harness refuse, while a run is active, the Read/Grep/Glob tools and any shell command that names those paths (`hooks/pre-read.js`, `lib/guards.js`). A hidden path inside the project is also made read-only, but a repo-wide Grep can still surface its lines, so keep it outside. This is the analogue of a train/test split: the agent iterates against the visible acceptance tests and is graded once on cases it has not seen.

## Tuning model and effort (`bin/tune.js`)
```bash
node .claude/harness/bin/tune.js --task-file spec.md --verify "node .claude/harness/bin/verify.js" \
  --candidates "claude-opus-5-5:low,claude-sonnet-5-5:low,claude-sonnet-5-5:high" --trials 2
```
Commit the spec and acceptance tests first: each trial runs `claude -p --model … --effort …` in a fresh worktree of `HEAD`, then the verify command grades it. Output is a table of pass rate, mean cost (from `--output-format json`) and mean time, the cheapest candidate that meets `--min-pass-rate` (default 100%), and `.harness/tune-report.json`. `--agent-cmd` replaces the default command (it receives `$HARNESS_MODEL`, `$HARNESS_EFFORT`, `$HARNESS_PROMPT_FILE`). This spends real tokens: use a small spec, and trials >= 2 when results are noisy. The rule of thumb to test is that a stronger model at low effort beats a weaker one at high effort on cost.

## Held-out tests: environment variable (`HARNESS_HIDDEN_DIR`)
The other way to hold out tests, besides `--hide` above. Use `--hide` when the harness starts the run; use this when you launch `claude` yourself and want the path kept out of `state.json` too. Both are enforced by the same read guards, and either can be used alone.
A visible acceptance suite can be read, and a strong model will satisfy it. A **held-out suite** checks the same rules on
inputs the agent has not seen, so "underspecified" actually bites. Put the tests in a directory **outside the project**,
and start the agent with the path in an environment variable that only the `claude` process carries:

```bash
HARNESS_HIDDEN_DIR=/abs/path/to/held-out claude -p "..."      # verify.config.json: "... \"$HARNESS_HIDDEN_DIR/*.test.js\""
```
While a run is active, shell commands and `Read`/`Grep`/`Glob` calls that name that directory or the variable are blocked
(`hooks/pre-read.js`, `lib/guards.js`). The held-out tests run inside `verify.js` (and so inside the Stop hook), and their
failing assertions come back in the verify output; that is the intended feedback channel. They resolve the project from the
current directory (`path.resolve('src/...')`), so they also run against the mutation copy. See [`fixtures/sheet-engine/`](fixtures/sheet-engine/).
Limits: this stops a good-faith agent from reading the suite, not a determined one, and every failure reveals one expected value.

## The cloud commit-check Stop hook and the work folder (#112)
The repeated "There are uncommitted changes in the repository. Please commit and push these changes to the remote
branch." message does **not** come from this harness. Claude Code cloud containers have their own Stop hook,
`~/.claude/stop-hook-git-check.sh`, registered in `~/.claude/launcher-settings.json` (which also denies edits to
it). It blocks every stop (exit 2) when the checkout has any of:
- **tracked changes**, staged or not;
- **untracked files** that are not gitignored (`git ls-files --others --exclude-standard`);
- **unpushed commits** on the current branch (and unsigned ones, where signing is on).

It stays quiet only when the stop already comes from a stop hook. The harness cannot change or turn it off and does
not try. Instead, helper agents keep unfinished work in **`.harness/work/<run>/`**: gitignored (the installer adds
`.harness/`, and `test/work-folder.test.js` checks that git does not list the folder in an installed project), and
writable during a run while the rest of `.harness/` stays read-only. Finished files move into the tree in one
commit. The rule is in `agents.md` and the `design-sessions` skill. Not ending a turn while helpers still run is #86.
Limits: symlinks are checked as they exist when the guard runs, so a link swapped in by a program the guard cannot
see gets through (as anywhere else in the project), and a link's target is checked as written, relative to the project
root, not to the link's own folder; `node -e` that mentions `.harness/` is still refused, so write
there with the Write tool or plain shell commands.

## Known limits (be honest about these)
- **Verify is only as strong as your tests.** With a plain `npm test` verify, an agent can pad with a placeholder test (seen live: `tests/smoke.test.js` asserting `true` passed an 80% coverage floor measured over test files). The strong verify closes that gap for Node projects; for other stacks write an equivalent gate. Acceptance tests written from the spec and protected with `--protect` remain the most important defence.
- **Shell guards are heuristic.** `lib/shell.js` is a best-effort parser, not a shell: variable indirection (`X=main; git push origin $X`), decoded payloads, and scripts written then executed get through. Pair with isolation (container/worktree, no prod credentials, network allowlist) and server-side branch protection + required CI.
- **Known gaps found by review and left open** (documented, not fixed): `git apply`/`patch`/`tar -C`/`unzip -d`/`find -exec` writes into protected paths; a read-only `node -e` that merely mentions a protected path is blocked (false positive, by design); `--force-with-lease` is blocked even on feature branches. Closed since: bulk staging of `.env` (`git add -A`, `commit -a`), `git clean`, deleting or moving `main`, `core.hooksPath` and `HUSKY=0`, `pkill`/`killall`, `>|` redirects. Bulk-staging detection runs `git status`, so a secret that is gitignored is correctly not flagged.
- **Allow list no longer has `Bash(node:*)`.** It let any `node -e` script bypass the shell guards. Only `node --test` and the harness `report.js` / `verify.js` are pre-approved; anything else asks.
- **Hiding is heuristic.** The agent can still find a hidden path by guessing at it from the shell in ways the parser cannot see (see the shell-guard limit above). Isolation is the real answer; hiding raises the cost of overfitting, it does not make it impossible.
- **Replicates add test-suite time** (default 2 runs per Stop attempt). Set `replicates: 1` for very slow suites.
- **Diagnosis relies on `node:test` output** for grouping (spec or TAP reporter); other output falls back to the raw tail.
- **Checkpoints are local unless `--checkpoint-push`.** A local ref survives a crashed agent or lost context, not a lost container. `restore` copies files back but does not delete files created after the checkpoint. Gitignored files are not captured.
- **The Stop feedback sends the full spec once** (first block); later blocks carry only a pointer plus the verify-output tail, so context does not grow by one spec copy per iteration.
- **Hooks fail open** on internal crashes (exit 1) so a bug cannot brick a session (each crash is written to `.harness/hook-errors.jsonl` and shown in the report). A *corrupt state file* is stricter: guards stay on, commits are refused, and the Stop hook blocks once (then lets the session end, since the agent cannot repair `.harness/`).
- **Gate files are always read-only during a run**: `verify.config.json`, `acceptance/` and `spec.md` are protected by default, in addition to any `--protect` paths.
- **Timeouts:** verify defaults to 600 s (`--verify-timeout SECONDS` to change); the Stop and commit hooks time out at 900 s in `settings.json`. Keep the verify budget (tests plus mutation samples) below that.
- **Per-edit lint:** `init --lint "<cmd>"` runs the command after every Write/Edit (`hooks/post-edit.js`) and sends failures back to the agent with exit 2. Exit 1 would not block.
- **Sandbox:** `settings.json` enables the OS sandbox for Bash and its child processes (credential dirs unreadable, network limited to npm and GitHub). Hooks cannot see what `npm test` reads; the sandbox can. **It needs `bwrap` and `socat`; without them Claude Code silently runs commands unsandboxed** and only the deny rules and shell guards apply. `init` warns when this is the case, and `init --require-sandbox` refuses to start instead. Verify the key names against your Claude Code version.
- **Trust the workspace first.** Non-interactive runs (`claude -p`) ignore the project `permissions.allow` list until the workspace is trusted, so the agent cannot even run `node --test` or `verify.js` and is graded blind (seen live: the Stop hook still passed the run, but the agent could not test its own work). Open Claude Code in the project once and accept the trust dialog, or set `projects["<dir>"].hasTrustDialogAccepted` in `~/.claude.json`. `init` warns when the workspace is not recorded as trusted.
- **Failure output matters as much as the gate.** A live run showed an agent spending about ten attempts reading a verify tail that said only "tests failed (3 failing)". `verify.js` now ends with a "Failing tests" section (names, error, expected/actual), and the Stop hook forwards up to 70 lines / 5000 characters.
- **Every Stop attempt costs an iteration**, including when the agent stops to ask a human a question; with no human that is wasted budget, so tell the agent not to ask.
- **No cost cap yet.** Time and iterations are capped (`--max`, `--max-minutes`); dollars are not. Bound spend with account/session limits, and use `tune.js` to find a cheaper model/effort.
- **The time budget is checked at Stop attempts**, so one long agent turn can overrun it; it is not a watchdog.
- **No evaluator-score gate yet.** `gan-evaluator` feedback is advisory; only the verify command is enforced.
