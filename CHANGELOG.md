# Changelog

## Unreleased

### Added

- **Change-request runs** (#89, spec #88): `pipeline.js check --product <dir> --docs <dir> --change <N>` walks one change of an accepted product on its own spec issue #N: `spec`, gate `spec-approved` on #N, `plan`, `build`, `review`, `qa`, `release`, gate `accepted` on #N. Waiting, layer verdicts, redirects (problem, impression and approach to the change's `spec`; correctness and craft to `build`), the 3-round limit, approvals tied to file hashes and the freeze of the product's gate files (`AMEND:` lines in the change's own `decisions.md`, frozen from the change's first check) reuse the first-run machinery, parameterised by issue, records folder (`<docs>/changes/<N>/`) and state file (`.harness/pipeline/<slug>.change-<N>.*`). The first run's records and state are only read. A change run is refused (exit 2) while the first run is not accepted or when `<N>` is the first run's spec issue. New `test/pipeline-change.test.js`; `orch-product-team` has a "Change requests" section; glossary terms **Change request** and **Change run**. First-run behaviour is unchanged.
- **Stack chosen at kickoff from an adapter catalogue** (#62, spec #55): new `.claude/harness/adapters/catalogue.json` (stacks, product kinds, checks provided and missing, fixture, status) with `node` proven, `vitest-stryker` and `junit` experimental, and Python, Rust, .NET, Expo/React Native, Electron and WeChat planned; `test/catalogue.test.js` checks that every proven or experimental fixture exists and that no always-loaded rule refers to the catalogue. `pipeline.js` keeps the design phase incomplete until `design.md`'s `## Stack` section names a catalogue adapter with its status (`Adapter: <id> (<status>)`) or records an unsupported-stack option (`Unsupported: <stack>; option: supported alternative|weaker gate|adapter first`); the spec-approved page gets a `### Stack` part under "The real choices"; the page part names an alternative and, for an unsupported stack, the three options; a weaker gate is approved in `design.md`'s Stack section (`option: weaker gate` and `Weaker gate: <checks>`, hashed with the `spec-approved` approval), and `weakerGate.missing` must match it exactly; the plan phase needs the chosen `adapter` in `verify.config.json` (none counts as `node`) and freezes the adapter's tool configs (`lib/protected.js`, dot folders included, configs named in commands at their exact path) by hash with the `AMEND:` rule. **Breaking for product runs in progress:** a `design.md` without a `## Stack` section sends the run back to the design phase. `orch-product-team` documents proposing the stack, changing it before approval, and the approach redirect after.
- **`vitest-stryker` adapter and the `slug-react` fixture** (#60, spec #55): `"adapter": "vitest-stryker"` is a preset on the report contract: `runner: "vitest"`, default `testCommand` `npx vitest run`, a required type check (default `npx tsc --noEmit -p tsconfig.json`; `null`/`false` refused), Stryker on the vitest runner (`npx stryker run`, checkers off by default), `holdout.runner: "vitest"`, `journeys.runner: "playwright"`; other runners and `weakerGate` are refused. Test quality runs for it (the JS checker reads `.tsx`/`.jsx` tests), so the gate is full. From PR #16: `expect('a').toBe('a')`-style and typed `expect<T>(...)` tautologies are caught, `expect<T>(...)` counts as an assertion, and `testQuality.srcAliases` (e.g. `@/`) counts aliased imports as source references. With this adapter `stryker.conf.*`, `stryker.config.*`, `vitest.config.*`, `vitest.workspace.*`, `vite.config.*`, `tsconfig*.json` and `playwright.config.*` are protected: `harness.js init` adds them to the run's protected paths and `check-protected.js` adds them from the base branch's `verify.config.json`; protected entries with `*` match a file name at any depth. New fixture `.claude/harness/fixtures/slug-react/` (Vite 8, React 19, TypeScript 6, Vitest 5, Stryker 10.1.1, Playwright 1.63; dependencies in the fixture only, `node_modules` gitignored) passes the real gate at a 100% kill rate with a hidden holdout set and journey `J1`. `junit` is unchanged.
- **Gate judges mutation from Stryker's report** (#59, spec #55): with `"adapter": "junit"` and `mutation.command` (plus `mutation.testRunner`), the mutation step runs Stryker with a gate-written config file outside the project (`jsonReporter.fileName`, `incremental: false`) as the positional argument and `--testRunner --mutate --reporters json --checkers --tempDirName`, so the project's Stryker config is not read and `--incremental` is never passed. `--mutate` is a seeded sample of `mutation.samples` files from `srcDirs`. New pure reader `lib/reports/mutation-elements.js`: score = (Killed + Timeout) / (Killed + Timeout + Survived + NoCoverage) against `minKillRate`, CompileError/RuntimeError counted apart; `Ignored` mutants fail unless listed in `mutation.ignored` (printed as a weakening); a sampled file missing from the report, an unrequested file, a foreign `mutate` list or an incremental run fail; `mutation.budgetMs` (default 300000) exceeded fails with the time used. Mutation is then checked, so `weakerGate.missing` must no longer list it. TypeScript checker off by default. The sample uses #58's source file set (`.tsx`/`.jsx` for `vitest`); `mutation.exclude` leaves files out of it, and `mutation.exclude` and `mutation.ignored` join `coverage.exclude` in the closing `weakened (verify.config.json)` line. With `vitest` and a mutation command, `weakerGate.missing` is just `test-quality`. Source and test files that look for Stryker's active mutant (`__stryker__`, `STRYKER_ACTIVE*`) fail the step; a report listing one file under two spellings is refused. The `node` path is unchanged and refuses the new keys.
- **Gate reads test results from JUnit** (#57, spec #55, ADR-0003): `"adapter": "junit"` with a `runner` (`vitest`, `playwright`; `standin-pytest` is test-only) makes `verify.js` judge the main run, replicates, holdout (counts only) and journeys (ids from JUnit names) from a JUnit report in a gate-owned directory outside the project, under the trust rules: non-zero exit fails, reports older than the run, missing, malformed or disagreeing with the runner's stdout summary are rejected. Failures print as `not ok N - <name>` lines, so the breaker is unchanged. New dependency-free `lib/reports/` (JUnit reader, runner flags and summary readers, report runs), a shell stand-in runner in the tests, glossary terms **Adapter** and **Report contract**. Coverage, test quality and mutation are not run for this adapter until #58/#59, so the gate fails unless `weakerGate` records the owner decision listing exactly those checks. The `node` path is unchanged.
- **Spec-approved page; one-way and two-way decisions** (#47, spec #44): new template `.claude/harness/templates/spec-approved-page.md` with seven sections (problem and who it is for, not building, the real choices, screens, done means, what we're unsure about, who judges each layer). `pipeline.js` keeps phase 4a (`spec`) incomplete until `spec-approved-page.md` is in the docs folder with every section filled (no section empty or left with a `<placeholder>`) and no code block, and names each missing or unfilled section. `orch-product-team` fills the page from `brief.md`, `ux.md`, `design.md` and the one-way decisions, posts it on the spec issue, and its `decisions.md` table gains a `Door` column (`one-way` / `two-way`); only one-way rows go on the page.
- **Two owner gates in the product run** (#24, spec #19): `pipeline.js` now checks phase 4a (`decisions.md` records `Spec issue: #N` and the chosen `Look:`), the owner gate `spec-approved`, phase 4b (plan, whose task list must come from that spec issue), and the owner gate `accepted` between release and retro. A gate reads the spec issue's labels live through `gh` (or a saved copy via `--issue-json`, only while `gh` cannot reach GitHub); while the label is missing or GitHub is unreachable it reports `waiting for owner: spec issue #N needs label <gate>` and exits 3. The Stop hook accepts that only from `pipeline.js`: it holds the agent once to tell the owner, then lets the turn end with the run still active and no iteration spent; once the label is there the run moves on by itself. Each such stop is traced as a `gate-wait`, and `agents-kpi` reports the next human prompt as a gate response (`human.gateResponses`, `human.gateWaits`), not an intervention. Once `spec-approved` passes, the spec issue number is pinned in `.harness/pipeline/`; a pull request is never a spec issue; the Bash guard refuses `gh` commands that add or remove a gate label; and time spent waiting does not count against `--max-minutes`. `orch-product-team` principles and phase table describe the two gates; "Gate response" is in the glossary.
- **Live pull reads open PRs** (#41, spec #19): `tasks-sync.js pull` and `check` without `--from-json` also fetch the repository's open PRs (`gh api repos/{owner}/{repo}/pulls?state=open`, paginated) in the `pullRequests` shape, so an open, non-draft PR with a whole `Closes #N` line in its title or body marks the ticket `done` live, as it does from saved JSON. The REST API gives no closing references, so a PR linked only in GitHub's sidebar does not count live. An unreachable `gh` behaves as before.
- **Live task-list pull and `check`** (#21, spec #19, ADR-0001): `tasks-sync.js pull --spec <n>` without `--from-json` reads the spec issue's sub-issues, their native blockers and the state of outside blockers through `gh` (`--repo owner/name` for another repository), giving the same task list as the saved-JSON path. A missing, unauthenticated or offline `gh` exits 2 and suggests `--from-json`. New `tasks-sync.js check --spec <n> [--from-json f] [--file TASKS.md]` regenerates in memory and compares, ignoring the generated-at time: exit 0 on a match, 1 listing the differing task ids, 0 with a warning when GitHub is unreachable. The pipeline's plan phase now requires a task list generated from a spec issue and runs `check` on it (product or docs directory); its messages point at `tasks-sync pull` instead of `plan-to-tasks`.
- **Layout check** (#31, spec #27): `check-layout.js` + `lib/layout.js`, with this repo's policy in `.claude/layout.json`. The harness suite fails when `examples/` or `docs/product/` exists, or a tracked Markdown doc (not CHANGELOG.md, the vendored `plugins/`, or the retro-board brief's run record) cites `examples/` or `docs/product/`. `git show <rev>:` references are allowed. The `examples/<p>` and `docs/product/<slug>/` placeholders in `orch-product-team`, `product-scoper` and `ux-designer` are a listed exception that #32 removes.
- **Generated task list from GitHub issues** (#20, spec #19, ADR-0001): `tasks-sync.js pull --spec <n> --from-json <file>` writes `TASKS.md` from a spec issue's tickets in the format `next-task.js` already reads, with derived status (closed issue or a `Closes #N` commit = done; open blocker outside the spec = blocked). `TASKS.md` is now gitignored. Tracker setup for the vendored skills in `docs/agents/`, `GLOSSARY.md`, and an `## Agent skills` section in `CLAUDE.md`. Live `gh` pull and `check` follow in #21.
- **Derived status from open PRs and ticket branches** (#22, spec #19): an open, non-draft PR that closes `#N` (whole closing line in its title or body, or `closingIssuesReferences`, given as `pullRequests` in the JSON wrapper) makes the ticket `done`; a **ticket branch** (a local branch with a path segment `issue-<N>` or `issue-<N>-<slug>`) or its harness WIP checkpoint makes it `doing` unless something above makes it `done`, so `next-task.js` reports `IN_PROGRESS` after an interrupted session. Draft PRs and remote-tracking branches do not count. `loop-runbook.md` now pulls, takes the first ready task on a ticket branch, commits with `Closes #N` and pulls again instead of typing status; `templates/tasks.md` says the file is generated and how status is derived.
- **Rules and agents by task class** (owner decisions of 2026-11-22): `performance.md` routes work by task class (opus for coding and judgement, sonnet for checks and small edits, haiku for reports, fable only after owner approval on a `needs-fable` issue); new always-loaded `working.md` (English, glossary and ADRs, GitHub issues as tracker, session/PR/flag limits, spike before build, approvals and merge danger); every agent sets `model:` and `effort:`; new `spec-reviewer` agent for the spec axis beside `code-reviewer`; this repo enables `mattpocock-skills` in its own `.claude/settings.json`.
- **mattpocock-skills** (`plugins/mattpocock-skills`): a pinned, reviewed copy of Matt Pocock's engineering and productivity skills (MIT, upstream `abeeaf9`), listed as a second plugin in the marketplace. See its `VENDORED.md`.
- **packing-list** (`examples/packing-list`): a shareable trip packing checklist, built end to end by `orch-product-team` under the whole-pipeline gate. Run record in `docs/product/packing-list/`.
- **Harness:** browser journeys and an optional type check inside `verify.js` (seven checks), TypeScript support for `node:test` projects, a whole-pipeline stop gate (`pipeline.js`), an installer (`install.js`), and plugin packaging as `product-team`.

- **wiki** (`examples/wiki`, version 1.0.0): a local-first Markdown wiki. Notes are plain `<Title>.md` files in one vault folder. The browser UI provides `[[wikilinks]]`, backlinks, rename that rewrites links, Ctrl+K search, a graph view and conflict-safe saves. It runs on Node 22 with no dependencies and no build step, bound to loopback by default. See `examples/wiki/README.md` for run steps, limits and known limitations.

### Changed

- **Docs describe the two owner gates; the definition of done records the reopen** (#25, spec #19): the root README's opening and "Run the team" now say the owner is asked at two owner gates (`spec-approved`, `accepted`), what `waiting for owner` means and that a gate answer is a gate response. `docs/process/definition-of-done.md` records that its scope changed (agent definitions and gates, products in their own repository, retro-board as the test bench), that reopen trigger 2 fired, that the per-phase re-measurement (about $20, about 2.5 h) is owed, not run, and waits for the owner's approval, and that the full run in #37 will supply fresh evidence. The layout check gains `retiredPhrases` (whole words, any case, wrapped across lines) with `retiredPhrasesSkip`: this repo's policy fails when a current doc says "one human gate" or "no human input until final acceptance"; CHANGELOG.md and the run records under `docs/testbench/` are skipped.
- **`plan-to-tasks` is retired** (#23, spec #19, ADR-0001): the skill is deleted, so there is one way to make tickets. `orch-product-team` phase 4 now runs `planner`, then `/mattpocock-skills:to-tickets` (tickets as sub-issues of the spec issue, labelled `afk`/`hitl`), then `tasks-sync pull --spec <n>` for the generated `TASKS.md`; its output lists the spec issue and its tickets instead of a hand-written `TASKS.md`. `loop-runbook.md` and the root README (now 9 skills) say the same. The layout check gains `retiredNames`: this repo's policy fails when a current Markdown doc names `plan-to-tasks` (prose or path) or its skill folder comes back; CHANGELOG.md and the vendored `plugins/` are skipped, and ADR-0001 (history) is exempt from the name check only (`retiredNamesSkip`).
- **New products are built in their own repository** (#32, spec #27): `orch-product-team`'s "Starting the run" now picks the product's repository or a path the owner gives (with no target, it proposes a new repository named after the product and asks the owner once), installs the harness there, and runs `pipeline.js check --product <product-repo> --docs <product-repo>/docs/product/<slug>` inside it. The build-only run, the effort note, the root README's "Run the team", the harness README, `product-scoper`, `ux-designer` and the journeys template say the same. The layout check's temporary `placeholderFiles` exception is removed from `.claude/layout.json` and `lib/layout.js`: a path with a repository in front (`<product-repo>/docs/product/`) already passes, a bare `docs/product/<slug>/` fails.
- **retro-board is the test bench** (#31, spec #27): `examples/retro-board/` moved to `testbench/retro-board/` and its run records from `docs/product/retro-board/` to `docs/testbench/retro-board/` (with `git mv`, so history follows). The gate's UX file, journey comments, the tune kit (trial layout, prompts, graders, golden fixtures where a path must resolve), the `gate-retro-board` and `eval-kit-selftest` CI jobs, `orch-product-team`, `definition-of-done.md` and both READMEs use the new paths. `examples/` and `docs/product/` are gone. `retro.md` cites the removed `agent-runs.json` and `human-corrected.json` as `git show bfad3bb:docs/product/<file>`.
- **Gate setup examples are harness fixtures** (#30, spec #27): `examples/todo-api`, `examples/slug-ts` and `examples/sheet-engine` moved unchanged to `.claude/harness/fixtures/`, and the harness README links there. `install.js` does not copy `fixtures/` into other projects: they are specs and acceptance tests without `src/`, so a target's test runner would only find failing tests.

### Fixed

- **retro-board votes clicked faster than the server answers** (#28): vote requests could reach the server out of order, and an earlier answer flipped a later vote back on screen, so a quick "Remove vote" could be lost. Votes now go out one at a time and answers keep the votes still pending; `#votes-left` is `aria-busy` until they are saved. Journeys wait for that before a reload, restart or close, which removes the J5 flake.

### Removed

- **link-shortener, packing-list and wiki** (#29, spec #27): `examples/{link-shortener,packing-list,wiki}/`, their run records in `docs/product/`, `docs/product/agent-runs.json`, `docs/product/human-corrected.json`, and the `gate-link-shortener` CI job and required check. Git history keeps them (last at `bfad3bb`). `agents-kpi.js` reads the two JSON files only when passed `--finals` or `--human-corrected`, so nothing depends on them by default.
- The ECC catalogue beyond what `orch-product-team` calls (21 agents, 48 skills, 43 commands, the `orch-*` single-feature workflows): a full product run used none of it. `hello-overkill` moved to jyeann/HW-PIRPLE-1. `examples/notes-api` and a stale `HARNESS-DIAGNOSIS.md`.
